**Dify 把 RAG 变成了「上传文档 → 选分段模式 → 配置检索」三步操作。但选错模式，召回效果会差一大截。通用模式适合 FAQ，父子模式适合技术手册；向量检索擅长语义，全文检索擅长术语，混合检索才是官方推荐。这篇从原理到配置实操，帮你避开 90% 的坑。**

## 一、为什么需要知识库？

大模型有两个致命短板：**知识有时效性**（训练数据截止日期之后的事它不知道），**上下文有限制**（不可能把整个企业文档塞进 prompt）。RAG（Retrieval-Augmented Generation）就是来解决这两个问题的。

RAG 的核心流程三步走 [[1]](https://docs.dify.ai/zh/use-dify/knowledge/readme)：

1. **检索**：用户提问时，先从知识库中检索最相关的信息片段
2. **增强**：把检索到的信息与用户问题打包，作为增强的上下文发给 LLM
3. **生成**：LLM 基于这些上下文生成精准答案

这就像考试时允许带参考资料——不用死记硬背，但能快速翻到相关章节找到答案。

**典型应用场景** [[1]](https://docs.dify.ai/zh/use-dify/knowledge/readme)：

| 场景 | 说明 |
|------|------|
| 智能客服 | 基于产品文档、FAQ、故障排查指南智能回复 |
| 企业知识门户 | 员工快速查询公司政策与流程 |
| 内容生成 | 根据背景资料生成报告、文章、邮件 |
| 科研分析 | 检索总结学术论文、市场报告、法律文档 |

## 二、创建知识库的三种方式

Dify 提供三种创建路径 [[1]](https://docs.dify.ai/zh/use-dify/knowledge/readme)：

### 2.1 快速创建

最简单的方式：上传文档 → 设置处理规则 → 等待索引完成。适合新手和大多数场景。

### 2.2 知识流水线

知识流水线（Knowledge Pipeline）是 Dify 2025 年推出的可视化数据处理编排功能，把 RAG 的 ETL 流程变成可拖拽的画布 [[5]](https://dify.ai/blog/introducing-knowledge-pipeline)。

**核心能力**：
- **数据源插件**：支持本地文件（30+ 格式）、云存储（Google Drive、AWS S3、阿里云 OSS）、在线文档（Notion、Confluence、GitLab）、网页爬虫（Firecrawl、Jina）
- **处理节点**：解析、增强、切分、嵌入四个阶段可自由组合
- **可观测调试**：每个节点的输入输出可见，快速定位问题

**动态更新能力**：知识流水线支持增量处理——当数据源有新文档或改动时，只处理变化的部分，无需重建整个索引。这对企业知识库的持续维护至关重要 [[5]](https://dify.ai/blog/introducing-knowledge-pipeline)。

**适用场景**：需要对接多种数据源、有复杂数据清洗需求、需要持续增量更新的企业级应用。

### 2.3 连接外部知识库

通过 API 直接同步外部知识库（如 Notion、飞书），无需迁移数据。适合已有成熟知识管理系统的团队。

## 三、文档切分：两种分段模式

LLM 的上下文窗口有限，不可能把整个知识库塞进去。必须把长文档切成小块，检索时只召回相关片段 [[2]](https://www.cnblogs.com/JavaEdge/p/18726040)。

切分质量直接决定检索效果。切太大，噪音多；切太小，上下文丢失。Dify 提供两种分段模式。

### 3.1 通用模式

**原理**：按规则把文档切成独立分段，检索时召回最相关的 TopK 个分段发给 LLM。

**配置项** [[2]](https://www.cnblogs.com/JavaEdge/p/18726040)：

| 配置 | 默认值 | 说明 |
|------|--------|------|
| 分段标识符 | `\n` | 按段落分块，支持正则表达式 |
| 分段最大长度 | 500 Tokens | 超出强制分段，上限 4000 Tokens |
| 分段重叠长度 | 建议 10-25% | 段与段之间的重叠，提高召回 |
| 文本预处理 | 可选 | 过滤空格、URL、邮件地址 |

**适用场景**：段落相对独立的文档，如 FAQ、政策条款、产品说明。

### 3.2 父子模式（推荐）

**原理**：双层分段结构，兼顾精准匹配和完整上下文 [[2]](https://www.cnblogs.com/JavaEdge/p/18726040)。

- **子分段**：小文本单元（如句子），用于精准检索
- **父分段**：大文本单元（如段落），提供完整上下文

**工作流程**：
1. 用户提问 → 系统用子分段精准匹配
2. 找到匹配的子分段 → 取出对应的父分段
3. 把父分段发给 LLM → 保证上下文完整

**类比**：在图书馆找资料，先通过索引卡片（子分段）定位到具体段落，再把整本书（父分段）拿过来读。

**父分段选项** [[2]](https://www.cnblogs.com/JavaEdge/p/18726040)：

| 选项 | 说明 | 适用场景 |
|------|------|----------|
| 段落 | 按分隔符切分段落 | 大文本、段落独立 |
| 全文 | 整篇文档作为父分段（限 10000 Tokens） | 小文本、段落关联紧密 |

**子分段配置**：
- 分段标识符默认为句子级别
- 最大长度默认 200 Tokens

**适用场景**：技术手册、操作指南、法律条文——用户问题往往指向具体句子，但回答需要完整段落背景。

**重要限制**：父子模式仅支持「高质量索引」，选定后无法切换为通用模式 [[2]](https://www.cnblogs.com/JavaEdge/p/18726040)。

## 四、索引方式：高质量 vs 经济

### 4.1 高质量索引

使用嵌入模型（Embedding Model）将文本转化为向量，存储到向量数据库。支持三种检索策略 [[3]](https://docs.dify.ai/zh-hans/guides/knowledge-base/create-knowledge-and-upload-documents/setting-indexing-methods)：

- 向量检索
- 全文检索
- 混合检索

**优点**：语义理解能力强，支持多语言、跨语言检索
**缺点**：消耗计算资源，需要嵌入模型 API

### 4.2 经济索引

不使用嵌入模型，仅支持全文检索（关键词匹配）。

**优点**：资源消耗低，速度快
**缺点**：无法理解语义，只能匹配关键词

## 五、检索策略：向量、全文、混合

### 5.1 向量检索

**原理**：把文本和问题都转化为向量，计算相似度匹配 [[3]](https://docs.dify.ai/zh-hans/guides/knowledge-base/create-knowledge-and-upload-documents/setting-indexing-methods)。

**优势**：
- 语义理解：即使没有出现确切词汇，也能通过语义关联找到答案
- 跨语言：不同语言之间的意义转换，适合多语言场景

**劣势**：
- 低频词匹配弱：专业术语、人名可能匹配不准
- 计算资源消耗大

### 5.2 全文检索

**原理**：倒排索引，搜索引擎的标准技术 [[3]](https://docs.dify.ai/zh-hans/guides/knowledge-base/create-knowledge-and-upload-documents/setting-indexing-methods)。

**优势**：
- 精准匹配关键词
- 低频词匹配强
- 资源消耗低

**劣势**：
- 无语义理解
- 无法处理同义词、跨语言

### 5.3 混合检索（推荐）

**原理**：同时执行向量检索和全文检索，综合排序 [[3]](https://docs.dify.ai/zh-hans/guides/knowledge-base/create-knowledge-and-upload-documents/setting-indexing-methods)。

**权重设置**：
- 语义值设为 1：仅向量检索
- 关键词值设为 1：仅全文检索
- 自定义权重：调整两者比例，找到最佳平衡

**Dify 官方推荐混合检索模式**，因为向量检索擅长语义理解，全文检索擅长精准匹配，两者互补 [[4]](https://www.53ai.com/news/dify/2024082864219.html)。

## 六、Rerank 重排：检索的最后一步优化

混合检索返回的结果可能排序不够精准。Rerank 模型对召回结果进行二次排序，提升相关性 [[3]](https://docs.dify.ai/zh-hans/guides/knowledge-base/create-knowledge-and-upload-documents/setting-indexing-methods)。

**工作原理**：
1. 混合检索召回 TopK 个分段
2. Rerank 模型计算每个分段与问题的相关性分数
3. 按分数重新排序，返回最相关的结果

**配置要求**：
- 需要在「设置 → 模型供应商」配置 Rerank 模型 API
- 若嵌入模型为多模态，需选择多模态 Rerank 模型
- 开启后消耗 Rerank 模型 Token

**推荐模型**：Jina AI 的 Rerank 模型，在 Dify 中表现良好 [[4]](https://www.53ai.com/news/dify/2024082864219.html)。

## 七、实战流程：从上传到测试

### 7.1 创建知识库

1. 进入「知识库 → 创建知识库」
2. 选择创建方式（快速创建/知识流水线/外部知识库）
3. 上传文档（支持 TXT、Markdown、PDF、Word 等）

### 7.2 配置分段与索引

**实际操作示例：构建技术文档知识库**

假设你有一份 50 页的 API 文档，按以下步骤配置：

**步骤 1：选择分段模式**
- 选择「父子模式」（技术文档需要句子定位 + 段落上下文）
- 父分段选择「段落」，分隔符用默认的 `\n`
- 子分段分隔符用默认的句子级别

**步骤 2：预览分段效果**
- 点击「预览区块」查看分段结果
- 检查子分段是否合理切分到句子
- 检查父分段是否包含完整段落

**步骤 3：选择索引方式**
- 选择「高质量索引」（父子模式强制要求）
- 选择嵌入模型：推荐 `text-embedding-3-small`（性价比高）或 `BGE-large-zh`（中文效果好）

### 7.3 配置检索策略

**推荐配置：混合检索 + Rerank**

1. 检索模式选择「混合检索」
2. 权重设置：语义 0.7，关键词 0.3（技术文档术语多，关键词权重适当提高）
3. 开启 Rerank，选择 `Jina-reranker-v2-base` 模型

### 7.4 测试召回效果

创建完成后，进入「召回测试」[[1]](https://docs.dify.ai/zh/use-dify/knowledge/readme)：

**测试用例设计**：
| 问题类型 | 示例问题 | 期望召回内容 |
|----------|----------|--------------|
| 功能查询 | 如何获取用户列表？ | API 端点说明段落 |
| 参数查询 | 分页参数怎么传？ | 参数说明表格 |
| 错误排查 | 返回 401 怎么办？ | 认证错误处理章节 |

**测试步骤**：
1. 输入测试问题
2. 查看召回的分段内容
3. 评估相关性：召回的分段是否包含答案？
4. 调整配置：如果召回不相关，尝试调整权重或分段规则

## 八、最佳实践

### 8.1 分段模式选择

| 文档类型 | 推荐模式 | 理由 |
|----------|----------|------|
| FAQ、政策条款 | 通用模式 | 段落独立，无需上下文 |
| 技术手册、操作指南 | 父子模式 | 需要句子定位 + 段落上下文 |
| 学术论文、法律文档 | 父子模式 | 专业术语多，上下文重要 |

### 8.2 检索策略选择

| 场景 | 推荐策略 | 理由 |
|------|----------|------|
| 多语言知识库 | 向量检索 | 跨语言语义理解 |
| 专业术语密集 | 混合检索 + Rerank | 语义 + 关键词互补 |
| 通用场景 | 混合检索 | Dify 官方推荐 |

### 8.3 元数据增强检索

元数据是「关于数据的数据」——给文档打标签，实现精准筛选 [[6]](https://docs.dify.ai/zh/use-dify/knowledge/metadata)。

**字段类型**：
| 类型 | 说明 | 示例 |
|------|------|------|
| 字符串 | 文本值 | author: "张三" |
| 数字 | 数值 | version: 2.0 |
| 时间 | 日期时间 | update_time: "2026-04-01" |

**应用场景**：
- 按部门筛选：只检索「产品部」相关的文档
- 按时间筛选：只检索「最近一个月」更新的内容
- 按版本筛选：只检索「v2.0」版本的手册

**操作步骤**：
1. 进入知识库 → 设置 → 元数据管理
2. 新建元数据字段（如 department、version）
3. 为每篇文档编辑元数据值
4. 在应用中集成知识库时，设置元数据筛选条件

### 8.4 避坑指南

1. **分段不要太大**：噪音多，影响检索精度
2. **分段不要太小**：上下文丢失，回答不完整
3. **测试召回效果**：上线前必须测试，调整配置
4. **定期维护知识库**：更新文档、删除过期内容 [[1]](https://docs.dify.ai/zh/use-dify/knowledge/readme)
5. **善用元数据**：给文档打标签，实现精准筛选，减少无关召回 [[6]](https://docs.dify.ai/zh/use-dify/knowledge/metadata)
